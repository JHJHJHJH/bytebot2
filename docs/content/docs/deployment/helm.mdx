Helm provides a simple way to deploy Bytebot on Kubernetes clusters.

## Prerequisites

- Kubernetes cluster (1.19+)
- Helm 3.x installed
- kubectl configured
- 8GB+ available memory in cluster

## Quick Start

<Steps>
  <Step>

  ### Clone Repository
    ```bash
    git clone https://github.com/bytebot-ai/bytebot.git
    cd bytebot
    ```
  </Step>
  
  <Step>

  ### Install Bytebot
    ```bash
    helm install bytebot ./helm \
      --namespace bytebot \
      --create-namespace
    ```
  </Step>
  
  <Step>

  ### Access Bytebot
    ```bash
    # Port-forward for local access
    kubectl port-forward -n bytebot svc/bytebot-ui 9992:9992
    
    # Access at http://localhost:9992
    ```
  </Step>

  <Step>

  ### Add Model Provider Keys
    Open [http://localhost:9992/models](http://localhost:9992/models), add an Anthropic, OpenAI, or Gemini API key, and test the connection before creating your first task.
  </Step>
</Steps>

## Basic Configuration

### Model Provider Keys

LLM provider API keys are no longer required in Helm values or Kubernetes Secrets for normal deployments. Install Bytebot first, then register provider keys from the UI at `/models`.

The chart mounts a persistent config volume for the agent by default so keys entered in `/models` survive pod restarts:

```yaml
bytebot-agent:
  persistence:
    enabled: true
    size: "1Gi"
```

### UI Admin Login (Optional)

Set both `adminUser` and `adminPassword` to require a login before users can
open the Bytebot web UI:

```yaml
bytebot-ui:
  auth:
    adminUser: "admin"
    adminPassword: "change-me"
```

For production, keep the credentials in an existing Kubernetes Secret:

```bash
kubectl create secret generic bytebot-ui-auth \
  --namespace bytebot \
  --from-literal=admin-user="admin" \
  --from-literal=admin-password="change-me"
```

```yaml
bytebot-ui:
  auth:
    existingSecret: "bytebot-ui-auth"
    usernameKey: "admin-user"
    passwordKey: "admin-password"
```

### Resource Limits (Optional)

Adjust resources based on your needs:

```yaml
# Desktop container (where automation runs)
bytebot-desktop:
  resources:
    requests:
      memory: "2Gi"
      cpu: "1"
    limits:
      memory: "4Gi"
      cpu: "2"

# Agent (AI orchestration)
bytebot-agent:
  resources:
    requests:
      memory: "1Gi"
      cpu: "500m"
```

### External Access (Optional)

Enable ingress for domain-based access:

```yaml
ingress:
  enabled: true
  host: bytebot.your-domain.com
  tls:
    enabled: true
```

### Local Access (Recommended)

kubectl port-forward -n bytebot svc/bytebot-ui 9992:9992

### External Access

## Verifying Deployment

Check that all pods are running:

```bash
kubectl get pods -n bytebot
```

Expected output:
```
NAME                              READY   STATUS    RESTARTS   AGE
bytebot-agent-xxxxx               1/1     Running   0          2m
bytebot-desktop-xxxxx             1/1     Running   0          2m
bytebot-postgresql-0              1/1     Running   0          2m
bytebot-ui-xxxxx                 1/1     Running   0          2m
```

## Troubleshooting

### Pods Not Starting

Check pod status:
```bash
kubectl describe pod -n bytebot <pod-name>
```

Common issues:
- Insufficient memory/CPU: Check node resources with `kubectl top nodes`
- No configured models: Open the UI at `/models`, add a provider key, and test it

### Connection Issues

Test service connectivity:
```bash
kubectl logs -n bytebot deployment/bytebot-agent
```

### View Logs

```bash
# All logs
kubectl logs -n bytebot -l app=bytebot --tail=100

# Specific component
kubectl logs -n bytebot deployment/bytebot-agent
```

## Upgrading

```bash
# Update your values.yaml as needed, then:
helm upgrade bytebot ./helm -n bytebot -f values.yaml
```

## Uninstalling

```bash
# Remove Bytebot
helm uninstall bytebot -n bytebot

# Clean up namespace
kubectl delete namespace bytebot
```

## Advanced Configuration

<Accordions type="multiple">
  <Accordion title="Optional Pre-seeded Provider Keys">
    For automated deployments, you can still pre-seed provider keys from Helm values or existing Kubernetes Secrets. This is optional; users can register keys from `/models` after deployment instead.
    
    ```yaml
    bytebot-agent:
      apiKeys:
        anthropic:
          useExisting: true
          secretName: "my-api-keys"
          secretKey: "anthropic-key"
    ```
    
    Create the secret manually:
    ```bash
    kubectl create secret generic my-api-keys \
      --namespace bytebot \
      --from-literal=anthropic-key="sk-ant-your-key"
    ```
  </Accordion>
  
  <Accordion title="LiteLLM Proxy Mode">
    For centralized LLM management, use the included LiteLLM proxy. Proxy provider credentials are configured on the proxy service, while standard Bytebot deployments can use `/models` instead:
    
    ```bash
    helm install bytebot ./helm \
      -f values-proxy.yaml \
      --namespace bytebot \
      --create-namespace \
      --set bytebot-llm-proxy.env.ANTHROPIC_API_KEY="your-key"
    ```
    
    This provides:
    - Centralized API key management
    - Request routing and load balancing
    - Rate limiting and retry logic
  </Accordion>
  
  <Accordion title="Custom Storage">
    Configure persistent storage:
    
    ```yaml
    bytebot-desktop:
      persistence:
        enabled: true
        size: "20Gi"
        storageClass: "fast-ssd"

    bytebot-agent:
      persistence:
        enabled: true
        size: "1Gi"
        storageClass: "fast-ssd"
    
    postgresql:
      persistence:
        size: "20Gi"
        storageClass: "fast-ssd"
    ```
  </Accordion>
  
  <Accordion title="Production Security">
    ```yaml
    bytebot-ui:
      auth:
        existingSecret: "bytebot-ui-auth"
        usernameKey: "admin-user"
        passwordKey: "admin-password"
    ```
  </Accordion>
</Accordions>
